These are local test credentials; passwords are stored as BCrypt hashes compatible with the API. Admin and Manager can use web login. Citizen uses the regular login endpoint. Existing users are preserved, including their passwords; a conflicting profile aborts the activity seed instead of changing access rights.

## Dataset

- 108 demonstration responsible entities: six types in each of the 18 mainland districts, with district geometries, example.com emails and explicitly fictitious addresses.
- 18 fictional occurrences: one per district, covering all six entity categories, six WAITING, six ACTIVE and six CLOSED cases, and all three priorities.
- 42 reports by Citizen: one for each WAITING event and three for each ACTIVE/CLOSED event. Each occurrence references its first report. Additional reports share its type and location, matching the API's proximity-based grouping.
- 24 feedback entries from Citizen and Manager, only for ACTIVE/CLOSED events, with positive and negative confirmations.

Dates are relative to the first seed execution, spread over the previous 18 days. Closed events end four hours after creation; open events use PostgreSQL `-infinity`, which Npgsql maps to the API's `DateTime.MinValue`. Priorities and radii follow the service rules for these report counts. Closed examples represent manual resolution, not the five-negative-feedback automatic closure threshold.

Reruns do not duplicate the activity dataset while its `[DEMO-SEED-XX]` occurrence titles remain unchanged. Existing occurrences are skipped, preserving application changes; renaming/removing those markers can cause replacement scenarios to be inserted. IDs are generated by PostgreSQL, and foreign keys are resolved from inserted records. No real incidents, notifications or external messages are created by the SQL.
